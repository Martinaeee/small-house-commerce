# Checkout 自动保存与后台草稿订单设计

日期：2026-11-03  
状态：待用户审阅；尚未实施、迁移或发布。  
审阅对象：店铺负责人及后续开发、验收人员。

## 1. 已确认的目标

消费者进入 Checkout 后即建立结账草稿；填写姓名、手机号、地址、日期、备注等内容时自动保存。即使信息不完整、格式暂时不符合正式下单要求、消费者没有点击 Review order 或 Place order，后台仍能查看已经保存的内容。

草稿必须与正式订单隔离：不占库存、不生成 PH 正式单号、不创建正式客户档案、不推送千易、不发送 Purchase、不计入正式订单数量或成交额。

同一次结账持续更新同一条草稿。正式下单成功后，该草稿关联实际订单并显示“已转订单”，不能再被迟到的自动保存请求改回未完成。

## 2. 现状核对与基线

生产核对基线为 `72711978e7fbafac274f59f61064b11ebf02c05b`。开发文档位于独立分支 `feat/checkout-draft-autosave-20261103`。实施和发布前仍须重新核对生产是否前进。

现有实现：

- `frontend/src/components/checkout/CheckoutForm.tsx` 仅在 `goToReview()` 校验成功后调用 `writeCheckoutDraft()`。
- `frontend/src/lib/checkoutDraft.ts` 将完整的确认页载荷写入当前标签页的 `sessionStorage`；不是服务端草稿，也不是输入时自动保存。
- `CheckoutConfirmView.tsx` 读取该载荷，通过现有幂等机制创建正式订单，成功后清理载荷。
- `PdpQuickCodOrder.tsx` 也使用这份本地确认载荷，不能直接改变其语义。
- `OrderStatus` 没有草稿状态。正式 `Order` 依赖客户、金额、地址快照、库存预留和风险分类，不适合承载只有半个手机号的表单。
- 后台订单工作台现有状态页签对应真实订单流程，不能把“草稿”塞入现有状态枚举。
- 现有隐私政策将姓名、手机号、地址等信息的收集时点描述为“下单时”，需要同步说明填写过程中保存未完成结账的行为。

## 3. 方案选择

### A. 独立结账草稿表与接口（采用）

保留原有正式下单链路，新增轻量草稿模块、前台同步层及后台只读查看页。允许不完整数据，生命周期和正式订单明确分离。

代价是需要新增数据库表、后端接口以及一次正式订单关联接入；好处是不会污染库存、客户分类、ERP 和成交统计。

### B. 给正式订单增加 DRAFT 状态（不采用）

会迫使现有客户、地址、金额、库存和订单状态逻辑兼容大量空字段，影响范围明显超过本需求。

### C. 只把表单实时存到浏览器（不采用）

可以辅助恢复输入，但后台看不到，不能满足用户要求。本方案仍保留本地暂存作为 A 的断网补充，而不是交付替代品。

## 4. 本次功能范围

### 4.1 前台触发与内容

- 覆盖 `/checkout` 和 `/checkout/confirm`。进入任一页面后建立或恢复当前结账尝试的草稿，不等点击提交。
- 商品尚在加载时允许草稿的商品列表暂为空；加载完成后更新同一条记录。
- 商品信息包括当前选购的 SKU 与数量；用于后台展示的商品名、变体、缩略图和参考价格由服务端读取商品资料生成，客户端报价不能成为正式金额依据。
- 保存可编辑表单的全部业务字段：姓名、手机号、省、市、Barangay、邮编、详细地址、配送日期、订单备注，以及优惠码输入值和已应用码。已删除或隐藏的字段不因本功能重新显示。
- 优惠码“正在输入的内容”和“已验证应用的码”分开保存。恢复输入不代表自动认定优惠有效，正式金额仍由原接口重算。
- 新增、修改、清空都需要同步。空字符串是明确清空，不得用“仅保存非空值”把旧地址或旧手机号留下。
- 草稿保留输入原文；不因手机号未输完、姓名暂为空等原因拒绝整个快照。正式格式校验仍在 Review order / Place order 按现有规则执行。
- 输入上限：姓名 120、手机号 24、省/市/Barangay 各 120、邮编 20、详细地址 255、备注 200、优惠码 32 个字符；商品最多 100 行、每行数量 1–99，请求体最多 64 KiB。前台控件与 DTO 同步约束，不接受任意额外 JSON 字段，不提供无限容量日志入口。

### 4.2 自动保存与故障处理

- 先恢复本地暂存，再启动服务端同步；禁止初始化时的空表单覆盖已保存内容。
- 每次输入变化立即更新浏览器本地暂存；停止输入约 600ms 后同步服务端。连续输入合并请求，同一页面不并行提交多个保存请求。
- 字段失焦、点击 Review order、页面进入后台等时机尝试提前同步。退出时的 `fetch(..., { keepalive: true })` 仅作补充，不能作为唯一保存手段。
- 保存失败不清空输入，也不阻止进入确认页或正常提交订单；保留待同步快照，联网恢复后重试，遵守服务端限流退避。
- Checkout 内容区增加轻量英文自动保存说明和状态：保存中、已保存、暂未同步。仅服务端确认后显示“已保存”，不把只写入浏览器当成后台已保存。
- 同一浏览器、相同选购范围可恢复最近的未完成内容；不把旧商品集合强行替换进本次 Checkout。不支持靠手机号在其他设备上读取草稿。
- 配送日期若恢复后已超出允许范围，继续沿用现有日期校验，不能静默宣称该日期仍可配送。

**可靠性边界：** 正常联网时边填写边保存。突然断网、进程被立即终止或设备断电时，不能保证最后尚未送达服务器的字符已经出现在后台；本地暂存用于下次进入后恢复、补传。浏览器禁用或清除存储时也不得承诺跨退出恢复。

### 4.3 本地存储与并发

- 新增独立、带版本和过期时间的自动保存存储，避免把半填写表单直接写进现有供确认页使用的 `luwag_checkout_draft`。
- 确认页原有完整载荷、正式订单幂等键、提交时 Meta 同意快照保持原语义。
- 每次结账尝试使用高熵随机能力令牌标识，刷新及失败重试复用；成功下单后清理该尝试的本地暂存及恢复索引。
- 不以手机号合并草稿，不把不同浏览器或不同选购范围拼成同一人。
- 请求携带版本信息，服务端原子拒绝旧版本覆盖；网络重试需幂等。若多标签页操作同一草稿产生冲突，不自动用旧整表覆盖新记录；保留本地未同步输入并提示重新加载，重新加载前告知存在未同步内容。

## 5. 服务端设计

### 5.1 独立模块与数据

新增 `CheckoutDraft` 数据模型及独立 `checkout-drafts` 模块，不复用 `OrdersService.checkout()` 创建草稿。

建议模型字段：

| 字段 | 用途 |
| --- | --- |
| id | 后台使用的独立 UUID，不是 PH 单号 |
| tokenHash | 能力令牌的 SHA-256，唯一；不落库原始令牌 |
| status | OPEN / CONVERTED / EXPIRED；EXPIRED 仅作无个人信息的防重标记，不显示在后台业务列表 |
| hasUserInput | 是否发生过顾客主动填写或选择；默认配送日期和自动加载商品不算 |
| version | 并发保护用版本号 |
| snapshot | 受 DTO 严格约束的原始业务字段和商品选择 |
| productSnapshot | 服务端生成的商品展示资料和参考金额 |
| contactName / contactPhone | 可为空、可不完整的后台搜索字段，不创建 Customer |
| orderId | 可空的正式订单关联；只允许从未关联变成关联，不得改挂其他订单 |
| createdAt / updatedAt / expiresAt | 生命周期与清理依据 |

按状态、最近更新、过期时间建立索引。订单关联不得使用删除草稿会级联删除订单的约束。无字段历史日志，不记录逐键输入轨迹。

### 5.2 公共接口

新增草稿 upsert 与读取接口，置于 `storefront/checkout-drafts` 路径下：

- 无需登录，但每次读取、更新必须持有当前草稿的高熵能力令牌。
- 令牌通过专用请求头传输，不放 URL、埋点、错误正文或访问日志；不能凭后台 UUID、手机号或订单号读取草稿。
- 第一次写入幂等建立记录，后续只更新同一令牌对应的 OPEN 草稿；版本比较与状态检查在数据库内原子完成。
- 对 CONVERTED 草稿的迟到请求返回已转订单状态，不再修改字段或重新建立 OPEN 记录。
- 明确处理版本冲突、过期、429 和暂时性错误，前台保留未同步输入。
- 响应使用 `Cache-Control: no-store`，不得让含个人信息的响应进入共享缓存。
- 限制新建频率、单令牌更新频率、IP 总频率及请求大小；使用现有限流基础设施，不记录原始手机号、地址或令牌作为限流日志。
- 更新只接收白名单表单字段和 SKU/数量，不接受客户端直接指定状态、关联订单或可信金额。

### 5.3 正式订单关联与竞态

正式下单请求增加可选草稿令牌；旧客户端和后台手工录单不传时保持兼容。

- 正式订单仍使用现有的内容指纹与幂等键；草稿令牌只是关联元数据，不加入订单内容指纹、不替代原幂等键。
- 正式订单事务成功时，按令牌哈希建立或更新草稿为 CONVERTED，并关联本次实际订单。
- 即使最早的自动保存请求尚未到达，也必须能建立同令牌的已转订单记录，防止稍后到达的首次保存产生虚假的未完成草稿。
- 转换状态与订单创建一起提交或回滚；订单失败时不能提前把草稿标为已转订单。
- 幂等重试返回原订单，不重复扣库存、不重复发送 Purchase、不让已关联草稿改挂另一订单。
- 已转订单草稿不可再次用于创建另一张订单；新的购买应建立新的结账尝试。
- 前台自动保存请求的超时、限流、失败不得成为正式下单的前置阻塞条件。正式订单自身校验和数据库错误仍按现有机制处理。

## 6. 后台查看方式

- 在现有订单页标题操作区增加“草稿订单”入口，进入独立 `/admin/orders/drafts` 页面；保留原订单状态页签、数量、列配置及 New Order 功能。
- 不修改全局 Header、Footer、后台导航和 shell。
- 列表显示：草稿标识、商品缩略图/名称/规格/数量、已填姓名、原始手机号、地址摘要、状态、最近更新时间、是否已转正式订单。
- 支持姓名/手机号搜索、状态筛选及分页，默认按最近更新时间倒序。
- 点击行查看完整已保存字段、商品清单、保存时间，以及已转订单时的正式订单链接。
- 未填写项显示“未填写”；不完整手机号照实展示，不伪装为有效可联系号码。
- 进入页面但未填任何信息的草稿也可查看，标明“尚未填写”，不能当作已识别客户。
- 超过 30 分钟无更新的 OPEN 草稿显示“未完成（30 分钟未更新）”提示；这是展示规则，不宣称客户一定已经退出，也不新增正式订单状态。
- 查看接口统一使用 JWT 和现有 `ORDER_VIEW_ALL` 权限。没有该权限既看不到入口，也不能直接读取列表或详情。
- 本期后台草稿页只读，不增加自动确认、自动推单、自动短信/邮件、批量导出或一键转正式订单。

## 7. 隐私与保留期限

- 前台明确告知结账资料在填写过程中自动保存，用于恢复未完成结账与提供相关协助，并链接隐私政策；不暗中扩大到表单以外的数据。
- 隐私政策更新收集时点、用途和保留期限。第一方结账保存不得被当成 Meta 同意、营销订阅或同意接受无关推广。
- 不把草稿手机号、地址、备注送入 Meta Pixel、CAPI 或分析事件。既有 InitiateCheckout 行为不因每次自动保存重复触发；草稿绝不触发 Purchase。
- 从未主动填写或选择任何字段的空草稿，自创建起保留至多 24 小时；系统默认日期、自动加载商品和普通读取不延长期限。含用户输入或已转订单的草稿，其快照最多保留至该次尝试创建后 30 天；正式订单本身继续遵循原有保留规则。
- 能力令牌包含该尝试的创建时间和至少 32 字节安全随机值，哈希覆盖完整令牌。服务端限制未来时钟偏差、校验最长 30 天寿命；客户端也按同一绝对期限淘汰本地副本，读取和重试不能无限续期。
- 空草稿 24 小时到期后清除全部字段、商品快照、搜索字段及订单关联，标记 EXPIRED，只保留防重需要的随机身份哈希、版本和时间；至该令牌 30 天失效时删除剩余标记。EXPIRED 请求不可恢复或改写快照，30 天后的旧令牌在查库前即被拒绝，避免清理后迟到请求复活旧草稿。
- 服务端定时清理过期草稿，本地暂存遵循相同期限；过期内容不继续显示或恢复。清理失败期间，读取、写入及后台查询也必须按期限拒绝使用过期内容。
- 清理沿用现有后台定时任务的生命周期模式，分批执行、可重复运行、失败后下次重试，不引入新的外部任务平台。
- 转换后的草稿到期清理不会删除或改写正式订单，也不清理其他业务表。

## 8. 验收标准

### 前台与恢复

1. 只进入 Checkout、尚未填写时，后台已有一条不影响正式业务的草稿。
2. 只填姓名、半个手机号、半段地址也能同步；修改和清空后后台值正确。
3. 尚未点击 Review order 就离开，后台仍可查看最近已确认同步的内容。
4. 相同结账刷新、返回、重试不重复新建；初始化不覆盖旧内容。
5. 本地存储不可用、接口失败、断网、429 时不清空输入、不阻塞正常下单；恢复后补传。
6. 桌面及手机验证草稿恢复、日期校验、地址级联清空和未应用优惠码输入的保存。
7. 旧确认页和 PDP 快捷下单的现有载荷语义不变；从快捷下单进入确认页时也能关联该次结账草稿。

### 后端与安全

8. 不完整字段可保存，超长/额外字段受限；无令牌、错误令牌、猜 UUID、不同浏览器不能读取别人的草稿。
9. 并发首次创建只落一条，同一版本重试幂等，乱序旧请求不能覆盖新内容。
10. 正式订单失败不转换；成功和幂等重试正确关联；先提交订单、后到首次保存也不会留下 OPEN 假草稿。
11. 已转换记录不重新开启、不改挂第二张订单；到期请求不能重新创建旧草稿。
12. 草稿请求前后客户、正式订单、库存预留、ERP 任务、Purchase outbox 和成交统计均不变化。
13. 权限隔离、分页、搜索、状态筛选、过期分批清理和本地 TTL 有自动测试。

### 回归与发布

14. 使用 TDD 覆盖新增协议、同步状态、API 和订单关联；运行前后端全量测试、类型检查、lint 和生产构建。
15. 浏览器验证实际 Checkout 与后台列表/详情；用隔离数据库测试创建、退出、恢复与正式下单闭环，不用真实客户数据做演示。
16. 发布前拉取并核对最新生产基线、Prisma generate、增量迁移、备份和前后端镜像恢复点；不得整体 seed 数据。

## 9. 变更边界与发布闸

预计涉及：新 Prisma 模型与增量迁移、新草稿模块和测试、正式下单 DTO/事务关联、前台同步工具与 Hook、Checkout/确认页、优惠码原始输入回调、后台列表/详情及入口、i18n、隐私说明、API/数据库文档。

明确不涉及：尺寸解析、商品编辑保存提示、全局视觉改版、现有订单状态重构、千易业务改造、自动弃单营销、跨设备手机号恢复。

本设计审阅通过后再编写实施计划并确认执行方式。没有审阅通过前不写业务实现；本文件不代表已执行或已授权生产迁移。生产新增表、启用自动采集前须确认发布范围，并保留关闭自动保存、回退应用镜像但不破坏正式订单的数据恢复方案。
